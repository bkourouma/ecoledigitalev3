# 1. Méthode de travail (apprise sur ce projet : respecte-la)

- Tu es superviseur. Délègue chaque chantier à un sous-agent (outil Agent, `subagent_type: general-purpose`, `model: sonnet`, `isolation: worktree`, `run_in_background: true`), plusieurs en parallèle quand les périmètres sont disjoints (6 à 8 agents simultanés au plus). Donne à chaque agent un prompt AUTONOME : rôle, première action (`git merge --ff-only feat/v2-phase-0`, car un worktree peut démarrer sur un ancien commit), documents à lire, mission précise, périmètre de fichiers, gates à garder verts, consigne de COMMITER à chaque lot vert (toutes les 30 à 45 minutes : les agents sont parfois coupés par des erreurs d'API ; l'identité de commit est passée en ligne : `git -c user.name=Claude -c user.email=noreply@anthropic.com commit` avec le trailer `Co-Authored-By: Claude <noreply@anthropic.com>`), interdiction de commiter `pnpm-lock.yaml`, interdiction de pousser, et un rapport final court.
- Si un agent est interrompu par une erreur d'API : regarde l'état de son worktree (`git -C .claude/worktrees/agent-<id> log --oneline feat/v2-phase-0..HEAD` et `status`), sauvegarde ses fichiers non commités par un commit WIP sur sa branche, reprends-le via SendMessage s'il a encore du contexte, sinon fusionne ce qui est cohérent et lance un agent neuf ciblé sur le reste (diagnostic précis des échecs dans le prompt).
- Les modèles de prompts qui ont bien marché sont dans l'historique du projet : un module = un schéma Postgres du même nom, plage de migrations réservée (tableau dans `module-conventions.md`), `manifest.ts`, `index.ts` public, domain pur, application (Result), infrastructure SQL via `TenantDb`, `http/plugin.ts` au contrat `(app, runtime)`, `subscribers.ts`/`jobs.ts`, `isolation-allowlist.<module>.ts` avec fixtures valides, README, audit via `runtime.auditPort`, tests unitaires + intégration réelle (Postgres éphémère) + `assertTenantIsolation`. Pour un nouveau module, commence par `pnpm module:new <clé>`.
- Fusion : tu fusionnes toi-même dans la branche courante. Conflits récurrents : `packages/contracts/src/v2/index.ts` -> régénère-le avec `node scripts/gen-contracts-index.mjs` ; `apps/web/messages/fr-CI.json` -> union des clés (JSON valide) ; `pnpm-lock.yaml` -> `pnpm install` après fusion, puis commit du lockfile ; `.env.example` et `package.json` -> garde les deux côtés. Après CHAQUE fusion : `pnpm install`, `pnpm check:boundaries`, `pnpm check:secrets`, type-check, et les tests concernés.
- Fichiers CRLF : utilise Python ou l'outil Edit pour les modifications de texte (sed casse parfois les fins de ligne).
- Écris le code en anglais (identifiants) et les libellés utilisateur en français (i18n `fr-CI`). Aucune règle réglementaire ou seuil académique en dur dans un module : tout passe par les RuleSets (`packages/rules-engine`, module `rules`). Montants XOF en entiers (`Money` du kernel). Aucune FK entre schémas de modules (sauf vers `kernel.tenants`).
- Quand une spec est manquante, fais-la rédiger d'abord par un agent « architecte de domaine » (spec.md, data-model.md avec DDL testé sur Postgres, plan.md, parity.md, open-questions.md) sous `specs/v2/`, puis implémente.

# 2. Questions métier : ne bloque jamais

Tu n'as personne à qui poser de question. Pour toute décision METIER non couverte par `specs/v2/DECISIONS-METIER.md` : applique la valeur par défaut proposée dans les `open-questions.md`, ou à défaut le comportement le plus prudent et réversible, et CONSIGNE la question dans `specs/v2/QUESTIONS-A-VALIDER.md` (numéro, contexte en langage non technique, options, valeur par défaut appliquée, fichier/module concerné). Ne fabrique jamais de règle officielle ivoirienne (MGA, CEPE, BEPC, BAC, passage/redoublement, barèmes) : implémente le MÉCANISME (RuleSet vide ou paramétré, jeux de données fictifs marqués comme tels), et liste dans `specs/v2/012-rules-engine/regulatory-sources-needed.md` ce qu'il faut obtenir.

# 3. Garde-fous à garder verts (après chaque fusion et en fin de chantier)

`pnpm check:boundaries` ; `pnpm check:secrets` ; `pnpm test:isolation` (avec Docker) ; `pnpm --filter @ecoledigitale/api type-check:v2` ; suite API complète via `with-postgres.mjs` ; `pnpm test:phase1` ; `pnpm test:characterization` ; `pnpm --filter @ecoledigitale/web test` ; build du worker (`pnpm --filter @ecoledigitale/worker build`) ; les erreurs `tsc` du code LEGACY (api 365, web 412) ne doivent pas augmenter.
