## Lecture

- **Origine** : migration où la table est créée (état final ; voir `renamed_from` dans le JSON). `prisma/migrations/...` = table connue uniquement de la chaîne Prisma.
- **tenant_id** : `req` = colonne NOT NULL ; `null` = colonne nullable (table globale à portée mixte) ; `ABSENT` = table globale. `RLS` : policy posée par les migrations (ne prouve pas l'isolation : l'API se connecte en super-utilisateur, cf. plan §2).
- **API rt** = fichiers d'exécution (routes/services/jobs/autres) ; la colonne « r/s/j » détaille routes / services / jobs. **Web** : pages / hooks / lib (+ composants et autres dans le JSON). Tests, scripts de seed et scripts racine sont comptés à part (`T` = tests API, `S` = scripts).
- Règle de comptage : un nom de table avec `_` compte pour toute occurrence en mot entier ; un nom d'un seul mot (`users`, `classes`, `documents`…) ne compte qu'en contexte SQL (`FROM|JOIN|INTO|UPDATE|TABLE|REFERENCES…`). Les occurrences « faibles » sont listées dans le JSON.

## Limites connues

- Les migrations sont rejouées dans l'ordre « préfixe numérique, puis nom » ; les fichiers `*_rollback.sql` et `validate_*` ne sont pas rejoués. L'ordre réel d'application en production n'est pas versionné (migrations appliquées à la main par `psql`, scripts `scripts/apply-migration-*.js`), et le déploiement exécute `prisma migrate deploy`.
- Les boucles `DO $$ ... EXECUTE format(...)` ne sont pas rejouables : seule celle de `0055_unified_multitenancy.sql` (ajout de `tenant_id` + RLS à toutes les tables existantes, sauf exclusions) est modélisée explicitement.
- Les occurrences en commentaire comptent comme références. Les noms de tables construits dynamiquement (`${table}`) ne sont pas détectés ; `getTableName(tenant, 'x')` l'est.
- `parser_unresolved` (JSON) liste ce que le parseur n'a pas su résoudre (9 entrées : `DROP TABLE` de tables jamais créées dans le dépôt, par exemple `attendance_records` ou les tables Imhotep déjà supprimées par `0051` que `0055` supprime à nouveau).
- Aucun `ALTER TABLE … RENAME` n'existe dans les 156 migrations rejouées ni dans la chaîne Prisma ; le parseur le gère (`renamed_from`), la liste est vide aujourd'hui.
- Les **vues** (`views` dans le JSON) ne sont pas des lignes de la matrice : `calendar_sessions` (0024, supprimée par 0027) et `v_payment_hour_details_enriched` (0103, lue par `routes/teacher-payments.ts:325`) sont les seules citées par le code.
- Les `CREATE TABLE` situés dans du code TS/JS (routes qui créent leurs tables au premier appel, scripts de migration) sont relevés : statut `runtime-ddl` quand la table n'existe nulle part ailleurs (`establishment_inbound_messages`, `student_replies`), sinon mention « DDL runtime » dans le champ `sources` du JSON (18 tables concernées, dont `teacher_attendance_sessions` et `notifications`).
