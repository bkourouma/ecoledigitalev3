# Parité legacy -> v2 — Module `attendance` (spec 010)

## 0. En-tête

**Objet.** Liste exhaustive de ce que le legacy EcoleDigitale fait en matière de présence (tables, fonctions, endpoints, règles implicites, seuils codés en dur, dette) et, pour chaque élément, son sort dans la v2 : conservé, amélioré, abandonné (avec justification) ou hors module (avec la spec porteuse). Le module v2 `attendance` remplace **quatre systèmes indépendants** du legacy par un modèle unique : *séance d'appel -> pointages par inscription -> justificatifs avec décision -> récapitulatifs dérivés + surcharge tracée*, plus la présence et les congés du personnel (absents du legacy).

**Sources.**
- Inventaire legacy vérifié (fichier:ligne) : `legacy-attendance.md` (IDs AT-001..AT-099, tables S1..S4, seuils §3, interface paie §4, présence du personnel §5, dette §6). Recoupements : `legacy-scheduling.md` §4 (séances Pro, SC-090..SC-111), `legacy-pro-enrollment.md` P-021.
- Cible : brief de conception (noms autoritaires, section « Module attendance » + « scheduling ») ; DDL de référence testé `attendance/0900..0903`, `scheduling/1002`, `scheduling/1003`.
- Spot-checks effectués dans le worktree : `routes/teacher-attendance.ts:479,704,1013` (`x-user-id`, `TODO admin`), `routes/parent-children.ts:311-316` (seuil 20 %), `routes/webhooks/livekit.ts:146,197,235` (seuil 50 %, pont), `routes/owner/index.ts:843`, présence de `teaching_hours` dans `0002_academic.sql:123-135`, absence de `student_period_attendance_summaries` dans `infra/scripts/migrations`.

**Conventions de chemins.** Sauf mention contraire, les chemins de code sont relatifs à `apps/api/src/` ; `0xxx_*.sql` = `infra/scripts/migrations/` ; `prisma/` = `apps/api/prisma/`. `S1..S4` = les quatre systèmes (S1 appel admin, S2 déclaration enseignant, S3 Professional par séance d'ECUE, S4 récaps par période).

**Légende des statuts.**
- **conservé** : reproduit à l'identique (règle métier maintenue).
- **amélioré** : reproduit avec correction ou enrichissement (bug corrigé, contrainte base, audit, configurable…) — la colonne « justification » dit lequel.
- **abandonné** : non reproduit (code mort, doublon, insécurité, hors périmètre produit, Imhotep…), justification donnée.
- **hors module -> NNN-nom** : relève d'un autre module/spec (017-scheduling, 032-payroll-port, 025-analytics, 013-report-cards…). Le détail du transfert est donné pour que la spec porteuse le reprenne.
- Quand une ligne couvre deux destinations, le statut porte la destination **principale** (celle qui porte la valeur métier) et la colonne « cible » cite l'autre.

**Comment lire.** §1 tables ; §2 fonctions/endpoints par famille (chaque ID AT-xxx de l'inventaire apparaît **exactement une fois** ; AT-053 regroupe cinq routes, AT-018/AT-019 deux sous-routes chacun) ; §3 règles implicites (R-xx) et bugs de l'inventaire §6 (B-xx) ; §4 seuils (S-xx) ; §5 synthèse chiffrée ; §6 écarts à trancher. Les IDs T-/R-/B-/S- sont propres à ce document (pour renvois et comptages).

**Principes v2 rappelés (pour comprendre les cibles).**
- UN modèle d'appel : `attendance.sessions` (OPEN -> SUBMITTED -> VALIDATED ; CANCELLED) -> `attendance.student_records` (UNIQUE session x inscription). Statuts = données (`status_definitions`) : PRESENT, ABSENT, LATE, EXCUSED, EARLY_LEAVE (élèves) ; PRESENT, ABSENT, LATE, ON_LEAVE (personnel). Un tenant ajoute des statuts (ex. MEDICAL_LEAVE), jamais ne modifie les statuts système.
- `EXCUSED` = absence justifiée par un justificatif **ACCEPTÉ** (CHECK base : `justification_id` et `original_status_code` non nuls). Jamais de motif libre sans décision.
- Aucun seuil ni équivalence (« 3 retards = 1 absence ») dans le module : RuleSet (012) ou configuration du consommateur. Seules configurations propres : `call_policies` (portée DAILY/SESSION/BOTH, `edit_window_minutes`, `late_requires_minutes`).
- Aucune FK inter-schémas : `academic` (année, classe, inscription, nœud), `people` (élève, personnel), `scheduling` (occurrence) référencés par UUID + API publique + événements.

## 6. Écarts et incohérences à trancher

| ID | Écart | Détail | Proposition |
|---|---|---|---|
| E-01 | Sémantique de `absent_minutes` : dérivé vs surcharge vs legacy | `attendance.summarize_enrollment` (0903) calcule `absent_minutes` = minutes des absences **non justifiées** seulement, `excused_minutes` à part ; la surcharge (`summary_overrides`) impose `excused_minutes <= absent_minutes` (inclusif, comme le legacy `justified_hours <= absence_hours`) ; le bulletin legacy affiche « N heure(s) dont M justifiée(s) » (N total). Une surcharge ne peut donc pas remplacer le dérivé sans changer de sens. | Fixer une seule définition : `absent_minutes` = total (justifié inclus), `excused_minutes` = sous-ensemble ; ajuster `summarize_enrollment` (et `period_summaries.absent_minutes`) ; 013 affiche N total dont M. |
| E-02 | Retard justifié : modèle non explicite | Le brief exige « retard justifiable » ; le DDL n'a qu'un `EXCUSED` (CHECK `justification_id` + `original_status_code`) et `is_justified` exige `counts_as_absence OR counts_as_late`. Deux options : LATE + `justification_id` (statut inchangé) ou statut EXCUSED avec `original_status_code='LATE'`. | Trancher en spec 010 ; recommandation : conserver LATE avec `justification_id` (le retard reste un retard, drapeau `is_justified` porté par le pointage), `late_minutes` déduits dans `summarize_enrollment`. |
| E-03 | Cas d'usage de lecture/pièce non listés au brief | `GET /sessions`, `GET /sessions/:id`, `GET /sessions/:id/records`, `GET /students/:id/records`, liste/détail des justificatifs, téléchargement et retrait de pièce n'ont pas de cas d'usage nommé dans « Cas d'usage » (seul `attachJustificationDocument` existe). | Ajouter : `listAttendanceSessions`, `getAttendanceSession`, `listStudentRecords`, `listJustifications`, `getJustification`, `getJustificationAttachment`, `removeJustificationAttachment`. |
| E-04 | Drapeaux par défaut des statuts de pack non fixés | Aucune donnée de pack dans 0900 (seed absent).
